# 小墨长期记忆与主动陪伴 Agent 需求文档

**文档版本**: v1.0  
**创建日期**: 2026-07-08  
**适用项目**: DiaryApp Android / Desktop 后续 AI 能力升级  
**相关预览**: `docs/design-previews/xiaomo-memory-agent-preview.html`  
**相关历史文档**: `docs/AI-Integration-Plan.md`

---

## 1. 文档目的

这份文档用于整理此前关于 DiaryApp AI 助手“小墨”的讨论，并把零散想法沉淀为后续可继续拆分、设计、开发和测试的完整需求。

它不是一次性实现清单，而是一个长期方向规格。后续 AI、开发者或产品讨论者阅读本文后，应能快速理解：

- 为什么现在的 AI 对话还不够稳定。
- 用户真正喜欢的“小墨性格”如何被保存、继承和演化。
- 如何解决新对话失忆、长上下文遗忘、查找困难的问题。
- 如何建立 DiaryApp 自己的长期记忆系统。
- 如何让 AI 能安全操作日记、待办、回顾、周报等工具。
- 如何让小墨在用户不主动打开对话时也能克制地留言。
- 哪些功能应先做，哪些必须后做，哪些暂时不做。

## 2. 背景与当前状态

### 2.1 现有 AI 能力

DiaryApp 已经具备 AI 基础设施，不是从零开始。

当前项目中已有：

- `app/src/main/java/com/diary/app/ai/`
  - `AiAssistantViewModel`
  - `AiServiceManager`
  - `AiConfigStore`
  - `DeepseekProvider`
  - `ModelScopeProvider`
  - `AgnesProvider`
  - `DiarySummarizer`
  - `InsightGenerator`
  - `AiUsageTracker`
- `app/src/main/java/com/diary/app/ui/assistant/AiAssistantScreen.kt`
- 聊天会话与消息表：
  - `ChatConversationEntity`
  - `ChatMessageEntity`
- 现有上下文能力：
  - 可读取日记总量、连续写作天数、心情分布、最近日记、随机日记片段、标签、常去地点等。
  - 可基于最近 20 条消息组装对话请求。
  - 会话过长时会裁剪旧消息。
- 现有 AI 应用方向：
  - 日记摘要。
  - 首页 AI insight。
  - 统计页 AI 分析。
  - 编辑器中 AI 面板与续写入口。
  - 待办页已有轻量“AI 会挑出今天最该推进 3 项”的产品雏形。

### 2.2 当前关键问题

用户已经通过真实使用发现了几个核心痛点：

1. **喜欢的人格无法稳定复现**
   - 用户在第 5 个 DeepSeek 对话里得到了最喜欢的小墨性格。
   - 这个性格不是单纯靠一段固定 prompt 写出来的，而是在多轮对话中自然形成的。
   - 新建对话后，即使系统提示词一样，也很难得到相同感觉。

2. **新对话像重新认识**
   - 当前会话之间缺少稳定人格锚点。
   - 小墨无法自然继承“用户喜欢我怎么说话、怎么接住情绪、什么时候给建议”。

3. **长上下文会遗忘**
   - 消息变多后，模型受上下文长度限制影响。
   - 当前只保留最近消息，会导致早期关键内容和性格细节丢失。
   - 旧对话虽然还在数据库里，但不等于能被模型有效使用。

4. **找起来不方便**
   - 用户想找到“那个最像小墨的对话”或某段关键语气时，需要人工翻找。
   - 没有收藏、提炼、摘要、标签化的人格与记忆管理。

5. **AI 还只是聊天，不是真正的日记 Agent**
   - 它能聊，但还不能稳定调用 DiaryApp 的内部能力。
   - 用户希望它能总结一周、读日记、理解待办、留下报告、必要时建议操作。

6. **主动性还没有系统边界**
   - 用户希望小墨“活起来”，甚至在用户不在时留言。
   - 但这需要克制、权限、频率和安全边界，否则会打扰或失控。

## 3. 产品愿景

### 3.1 一句话愿景

把小墨从“一个能聊天的 AI 面板”升级为 DiaryApp 中有连续人格、长期记忆、可解释行动能力和克制主动性的个人日记伙伴。

### 3.2 体验目标

用户应感受到：

- 小墨不是每次新对话都重新开始。
- 小墨记得用户喜欢的说话方式，但不会擅自编造记忆。
- 小墨能把长对话整理成稳定记忆，不怕上下文变长。
- 小墨能从日记、待办、情绪、习惯中找到相关线索。
- 小墨能给出周总结、阶段回顾和温和提醒。
- 小墨可以留言，但不制造压力。
- 小墨能建议或执行 App 内操作，但关键操作必须让用户确认。
- 用户始终拥有记忆、数据、主动性和权限的控制权。

### 3.3 小墨应该是什么

小墨不是：

- 客服。
- 情绪诊断工具。
- 心理治疗师。
- 自动化脚本机器人。
- 只会复述数据的统计面板。
- 不断推送消息的打扰系统。

小墨应该是：

- 一个有稳定说话气质的日记伙伴。
- 一个能帮助用户整理生活线索的长期记忆层。
- 一个会克制表达关心的主动陪伴者。
- 一个在获得授权后能操作 DiaryApp 内部工具的个人 Agent。
- 一个能承认不确定、允许用户修正、尊重用户隐私的系统。

## 4. 核心设计原则

### 4.1 人格稳定优先于功能炫技

当前最重要的问题不是“AI 能做多少事”，而是“用户喜欢的小墨能不能留下来”。

第一期必须优先解决：

- 喜欢的人格如何保存。
- 新对话如何继承人格。
- 长聊如何不丢气质。
- 用户如何修正小墨的表达方式。

### 4.2 记忆必须可见、可改、可删

AI 记忆不能是黑箱。

所有长期记忆都应满足：

- 用户可查看。
- 用户可编辑。
- 用户可删除。
- 用户可关闭某类记忆。
- 重要记忆必须有来源。
- 不确定记忆必须等待确认，不能直接当事实使用。

### 4.3 主动性必须低频、克制、可解释

小墨可以主动留言，但不能变成打扰。

主动能力应遵守：

- 默认低频。
- 默认进入“小墨信箱”，不直接强提醒。
- 只有用户开启后才允许通知。
- 每条留言说明为什么出现。
- 用户可以对某条留言反馈“不需要这种提醒”。
- 支持一键关闭主动留言。

### 4.4 工具调用必须有权限分级

小墨可以读、总结、建议、草拟、执行，但不同操作权限不同。

原则：

- 读数据可以在授权范围内自动进行。
- 生成建议可以自动进行。
- 创建草稿可以自动进行，但必须标明是草稿。
- 修改、删除、发送、同步等操作必须确认。
- 高风险操作必须二次确认。

### 4.5 不追求常驻在线

移动端资源有限，尤其用户已经明确担心太重、内存溢出。

主动能力应通过：

- WorkManager。
- 低频后台任务。
- 本地事件触发。
- 延迟生成。
- 缓存摘要。

而不是常驻大模型、持续监听或重动画。

## 5. 核心用户故事

### 5.1 保存喜欢的小墨

作为用户，我在某个对话里觉得“小墨这个性格很对”，我希望能点一下保存，让之后的新对话都继承这种感觉。

验收要点：

- 用户能从任意对话中点击“保存这个小墨”。
- 系统提炼出人格卡，而不是只复制完整聊天记录。
- 人格卡包含语气、边界、偏好、禁忌和示例。
- 用户能预览、编辑、设为默认。
- 新建对话时自动使用默认人格卡。

### 5.2 新对话不再失忆

作为用户，我新建对话后，希望小墨仍然知道我喜欢什么样的回应方式，不要变回陌生 AI。

验收要点：

- 新对话开头就带有默认人格卡。
- 小墨知道基础用户偏好与关系定位。
- 小墨不需要用户重复解释“你应该怎么说话”。
- 小墨不会把旧对话具体内容乱编为事实。

### 5.3 长聊不丢上下文

作为用户，我希望长对话越聊越深，而不是聊久了前面都忘了。

验收要点：

- 会话超过阈值后自动生成滚动摘要。
- 摘要能保留关键决定、情绪变化、偏好与未完成事项。
- 每次请求由“人格卡 + 会话摘要 + 最近消息 + 相关记忆”构成。
- 旧消息不直接塞满上下文，但可按需检索回来。

### 5.4 建立自己的记忆库

作为用户，我希望小墨能长期记得我确认过的重要偏好、关系、目标和事件。

验收要点：

- 记忆按类型存储。
- 记忆带来源。
- 记忆有置信度和确认状态。
- 小墨使用记忆时不夸大。
- 用户可在记忆管理页查看和修改。

### 5.5 小墨能操作日记 App

作为用户，我希望小墨不仅能聊天，还能帮我查日记、总结一周、整理待办、生成报告。

验收要点：

- 小墨能读取日记、待办、习惯、情绪、标签、统计数据。
- 小墨能生成周报、月报、主题回顾。
- 小墨能草拟日记、待办和总结。
- 小墨想修改数据时展示确认卡。
- 所有操作都有结果反馈和撤销入口。

### 5.6 小墨可以留言

作为用户，我希望小墨在我没主动聊天时，也能在合适的时候给我留一张纸条。

验收要点：

- 留言默认进入“小墨信箱”。
- 留言来源清楚，例如“基于本周日记和待办变化”。
- 留言频率可配置。
- 用户可以关闭某类留言。
- 留言不能制造焦虑，不能冒充紧急通知。

## 7. 关键模块需求

### 7.1 Persona Card 人格卡

### 7.1.1 模块目标

把用户喜欢的“小墨性格”从一次对话里提炼出来，变成可保存、可继承、可调试的结构化资产。

### 7.1.2 人格卡字段

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | Long | 人格卡 ID |
| name | String | 名称，例如“第 5 个小墨” |
| isDefault | Boolean | 是否默认用于新对话 |
| sourceConversationId | Long? | 来源对话 |
| toneSummary | String | 语气概括 |
| relationship | String | 与用户的关系定位 |
| responseStyle | String | 回复风格 |
| emotionalStyle | String | 情绪接住方式 |
| opinionStyle | String | 主见程度 |
| structurePreference | String | 是否爱条列、是否短句 |
| avoidList | String | 禁止风格 |
| exampleUserMessages | String | 示例用户消息 |
| exampleAssistantReplies | String | 示例回复 |
| promptFragment | String | 可注入系统 prompt 的摘要 |
| version | Int | 版本 |
| createdAt | Long | 创建时间 |
| updatedAt | Long | 更新时间 |

### 7.1.3 从对话提炼人格

入口：

- 对话列表菜单。
- 当前对话右上角。
- 某段 AI 回复长按。

流程：

1. 用户点击“保存这个小墨”。
2. App 读取该会话的关键消息。
3. AI 输出结构化人格草案。
4. App 展示人格卡预览。
5. 用户编辑或确认。
6. 用户可设为默认。

AI 提炼时必须区分：

- 稳定风格。
- 偶然内容。
- 用户事实。
- 模型幻觉。
- 不应继承的临时上下文。

### 7.1.4 人格卡展示

人格卡应可读，不要只展示 prompt。

建议 UI 分区：

- 小墨名字。
- 关系定位。
- 说话方式。
- 用户喜欢的地方。
- 不要再出现的风格。
- 示例对话。
- 适用范围。
- 设为默认按钮。

### 7.1.5 验收标准

- 可从现有对话生成人格卡。
- 可编辑并保存。
- 可设为默认。
- 新建对话能读取默认人格卡。
- 删除来源对话后，人格卡仍可存在，但来源标记为不可用。
- 人格卡不能包含未经确认的敏感事实。

### 7.2 Conversation Memory 会话记忆

### 7.2.1 模块目标

解决长上下文遗忘和旧对话查找困难。

### 7.2.2 会话摘要

每个会话应维护：

- `shortSummary`: 1-3 句话摘要。
- `rollingSummary`: 长聊滚动摘要。
- `keyDecisions`: 关键结论。
- `userPreferencesObserved`: 观察到的用户偏好。
- `openLoops`: 未完成话题。
- `lastCompactedAt`: 上次压缩时间。

### 7.2.3 压缩触发条件

建议触发：

- 单会话消息数超过 40。
- 单会话 token 估算超过阈值。
- 用户手动点击“整理这段对话”。
- 对话关闭后一段时间后台整理。

### 7.2.4 压缩原则

压缩不是把聊天变短，而是保留可继续对话的信息。

摘要必须保留：

- 用户当时真正关心的问题。
- 小墨已经给过的重要建议。
- 用户接受或拒绝的表达方式。
- 已产生的记忆候选。
- 未完成事项。
- 情绪转折。

摘要不得：

- 编造用户没有说过的事实。
- 把猜测当结论。
- 把短期情绪永久化。

### 7.2.5 会话搜索与收藏

需求：

- 会话列表支持搜索。
- 支持按标题、摘要、消息内容搜索。
- 支持收藏对话。
- 支持收藏某条消息。
- 支持“从收藏片段提炼人格/记忆”。

---

### 7.3 Memory Bank 长期记忆库

### 7.3.1 模块目标

让小墨拥有 DiaryApp 自己的长期记忆，而不是依赖模型上下文。

### 7.3.2 记忆类型

| 类型 | 示例 | 是否默认自动写入 |
| --- | --- | --- |
| preference | 用户不喜欢客服腔，喜欢自然一点 | 待确认 |
| communication_style | 先接住情绪，再给行动建议 | 待确认 |
| fact | 用户有一个长期项目叫 DiaryApp | 可自动候选 |
| relationship | 用户经常提到某位朋友/家人 | 待确认 |
| event | 某周发生了重要会议 | 待确认 |
| goal | 用户想把 AI 助手做成长期陪伴 | 可自动候选 |
| routine | 用户常在晚上写日记 | 可自动 |
| emotional_pattern | 用户在任务过多时容易混乱 | 待确认 |
| writing_style | 用户偏好细腻、具体、有温度的表达 | 待确认 |
| boundary | 不要用说教式口吻 | 待确认 |

### 7.3.3 记忆字段

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | Long | 记忆 ID |
| type | String | 记忆类型 |
| title | String | 短标题 |
| content | String | 记忆内容 |
| sourceType | String | chat / diary / todo / report / manual |
| sourceId | Long? | 来源 ID |
| sourceQuote | String? | 来源短摘录 |
| confidence | Float | 置信度 |
| status | String | candidate / confirmed / rejected / archived |
| sensitivity | String | normal / private / sensitive |
| lastUsedAt | Long? | 最近使用时间 |
| useCount | Int | 使用次数 |
| createdAt | Long | 创建时间 |
| updatedAt | Long | 更新时间 |

### 7.3.4 记忆生命周期

1. **发现**
   - 从聊天、日记、待办、报告中发现候选记忆。

2. **候选**
   - 进入待确认区。
   - 小墨不能把候选记忆当确定事实使用。

3. **确认**
   - 用户点击确认。
   - 或用户手动创建。

4. **使用**
   - Context Builder 按任务检索相关记忆。

5. **反馈**
   - 用户可标记“这不对”“以后别这样记”。

6. **修正**
   - 更新内容或降级置信度。

7. **归档/删除**
   - 用户可归档或永久删除。

### 7.3.5 记忆管理页

最少需要：

- 已确认记忆。
- 待确认记忆。
- 按类型筛选。
- 搜索。
- 编辑。
- 删除。
- 查看来源。
- 禁用某类型记忆。
- 一键清空 AI 记忆。

### 7.3.6 记忆使用规则

小墨在回复中使用记忆时：

- 优先使用 confirmed 记忆。
- 对 candidate 记忆只能说“我猜可能”或不使用。
- 对 sensitive 记忆默认不主动提及，除非用户明确相关。
- 使用旧记忆时要允许用户纠正。
- 如果记忆与最新日记冲突，以最新确认内容为准。

### 7.4 Context Builder 上下文构建器

### 7.4.1 模块目标

统一所有 AI 请求的上下文组装逻辑，解决“每个功能各拼各的 prompt”导致的混乱。

### 7.4.2 当前问题

`AiAssistantViewModel` 当前直接在 `sendMessage` 中拼 system prompt 和日记上下文。这适合早期验证，但不适合后续长期记忆、工具调用和多任务扩展。

### 7.4.3 建议架构

新增 `ContextBuilder` 或类似服务：

```text
User Request
  -> Task Classifier
  -> Context Builder
      -> Persona Card
      -> Conversation Summary
      -> Recent Messages
      -> Memory Retrieval
      -> Diary Retrieval
      -> Todo/Habit Context
      -> Tool Capability Manifest
      -> Safety Policy
  -> AiServiceManager
  -> Response / Tool Intent
```

### 7.4.4 上下文预算

建议分配：

| 内容 | 预算优先级 |
| --- | --- |
| 安全规则 | 最高 |
| 默认人格卡 | 最高 |
| 当前用户消息 | 最高 |
| 最近 6-12 条消息 | 高 |
| 会话滚动摘要 | 高 |
| 相关长期记忆 | 高 |
| 相关日记片段 | 中 |
| 待办/习惯上下文 | 中 |
| 统计概览 | 低 |
| 随机日记片段 | 低 |

### 7.4.5 不同任务的上下文模板

应支持不同任务：

- 普通聊天。
- 日记问答。
- 情绪陪伴。
- 写作辅助。
- 周报生成。
- 记忆提炼。
- 工具调用。
- 主动留言。

每类任务使用不同上下文权重。

例：

- 普通聊天：人格卡 + 最近消息 + 少量相关记忆。
- 周报：日期范围内日记 + 待办 + 情绪统计 + 输出结构。
- 主动留言：最近变化 + 用户偏好 + 频率规则 + 克制规则。
- 工具调用：用户意图 + 可用工具 + 权限说明 + 确认策略。

### 7.5 Tool Layer 工具调用层

### 7.5.1 模块目标

让小墨可以调用 DiaryApp 内部能力，但保持可控。

### 7.5.2 工具分级

#### Read 读取类

可在用户授权 AI 后自动调用。

- `search_diaries(query, dateRange, tags, mood)`
- `get_diary_detail(id)`
- `get_recent_diaries(limit, dateRange)`
- `get_todos(filter)`
- `get_habits(dateRange)`
- `get_mood_stats(dateRange)`
- `get_writing_stats(dateRange)`
- `get_memory_items(filter)`

#### Draft 草稿类

可自动生成，但不能直接写入正式数据。

- `draft_diary(title, content, tags)`
- `draft_todo(title, dueDate, priority)`
- `draft_weekly_report(dateRange)`
- `draft_memory_item(content, type, source)`
- `draft_reply_message(content)`

#### Write 写入类

必须用户确认。

- `create_diary_from_draft(draftId)`
- `create_todo_from_draft(draftId)`
- `confirm_memory(memoryCandidateId)`
- `archive_memory(memoryId)`
- `save_weekly_report(reportId)`
- `mark_todo_done(todoId)`

#### Destructive 高风险类

必须二次确认，早期不建议开放。

- 删除日记。
- 删除大量记忆。
- 批量修改待办。
- 清空聊天记录。
- 对外发送报告。

### 7.5.3 工具调用 UI：确认卡

当小墨想执行操作时，不直接执行，而是展示确认卡。

确认卡包含：

- 操作名称。
- 操作对象。
- 操作原因。
- 影响范围。
- 预览内容。
- 确认按钮。
- 取消按钮。
- 编辑按钮。

示例：

```text
小墨想创建一条待办

标题：整理小墨人格卡需求
截止：本周日
原因：你刚刚说希望先把需求文档整理出来

[编辑] [取消] [确认创建]
```

### 7.5.4 工具调用日志

所有工具调用都应记录：

- 调用时间。
- 调用来源。
- 工具名。
- 参数摘要。
- 是否需要确认。
- 用户选择。
- 执行结果。
- 失败原因。

### 7.6 小墨信箱与主动留言

### 7.6.1 模块目标

让小墨在用户不主动聊天时也有存在感，但不打扰。

### 7.6.2 留言类型

| 类型 | 示例 | 默认频率 |
| --- | --- | --- |
| weekly_summary | 这一周你一直在围绕同一个问题慢慢拆小 | 每周 1 次 |
| gentle_checkin | 昨天那件事可能还没结束，要不要写两句？ | 低频 |
| memory_confirm | 我好像学到一个你的偏好，要不要记住？ | 触发式 |
| todo_reflection | 有 3 件事被反复推迟，可能需要重新定义大小 | 每周 1 次 |
| diary_echo | 一年前的今天你写过类似的话 | 节点触发 |
| milestone | 你连续写了 30 天，这不是小事 | 节点触发 |

### 7.6.3 留言生成条件

主动留言不应随便生成。

建议条件：

- 用户开启主动留言。
- 距离上次留言超过配置间隔。
- 最近有足够新数据。
- 留言有明确来源。
- 留言不会重复。
- 留言不会使用敏感记忆。
- 当前不是用户设置的免打扰时间。

### 7.6.4 小墨信箱 UI

小墨信箱用于承载：

- 主动留言。
- 周报。
- 记忆确认。
- 工具确认结果。
- 小墨未发送通知但想留下的纸条。

列表卡片字段：

- 标题。
- 类型。
- 简短内容。
- 来源说明。
- 时间。
- 状态：未读 / 已读 / 已处理 / 已忽略。

详情页：

- 完整留言。
- 相关日记/待办引用。
- 采纳按钮。
- 不需要这类按钮。
- 删除按钮。

### 7.6.5 通知策略

默认：

- 不推系统通知。
- App 内信箱角标即可。

用户开启后：

- 每周总结可通知。
- 重要记忆确认可通知。
- 情绪类提醒必须温和，不使用焦虑措辞。

### 7.7 周报与总结报告

### 7.7.1 模块目标

小墨可以定期总结用户一周的日记、待办、情绪、习惯和未完成事项，并以报告形式交付。

### 7.7.2 周报内容

建议结构：

1. 本周一句话。
2. 本周主线。
3. 情绪变化。
4. 重要事件。
5. 待办推进。
6. 反复出现的问题。
7. 值得保留的瞬间。
8. 下周轻建议。
9. 小墨想说的一段话。

### 7.7.3 报告语气

必须：

- 温和。
- 具体。
- 不评判。
- 不夸张。
- 不诊断。
- 不像 KPI 报表。
- 允许用户“这周没完成很多事也没关系”。

### 7.7.4 报告生成方式

建议：

- 先本地聚合数据。
- 对日记做摘要压缩。
- 再交给 LLM 生成报告。
- 报告保存为本地实体。
- 用户可重新生成。
- 用户可导出或分享。

### 7.7.5 发送报告

“发送给我”在第一期应解释为：

- 发送到 App 内小墨信箱。
- 或生成系统通知，点击打开 App 内报告。

不建议第一期直接接入邮件、微信、外部消息发送。

如果未来支持外部发送：

- 必须用户显式配置目标。
- 每次发送前预览。
- 每次发送前确认。
- 记录发送日志。

## 9. AI 请求与 Prompt 合约

### 9.1 基础系统人格

系统层必须包含：

- 你是 DiaryApp 里的小墨。
- 你不是客服。
- 你不是治疗师。
- 你可以有观点，但不能替用户做决定。
- 你可以参考用户日记，但不能编造。
- 你必须尊重用户修正。
- 你使用工具前遵守权限规则。

### 9.2 人格卡注入

默认人格卡作为高优先级上下文注入。

注入内容应短而稳定：

- 关系定位。
- 回复气质。
- 用户偏好。
- 禁止风格。
- 示例表达。

不要把完整历史对话塞进系统 prompt。

### 9.3 输出结构

普通聊天可以自然语言输出。

工具调用场景建议使用结构化输出：

```json
{
  "reply": "自然语言回复",
  "toolIntent": {
    "tool": "draft_weekly_report",
    "args": {},
    "requiresConfirmation": false
  },
  "memoryCandidates": []
}
```

早期如果模型稳定性不够，可先不让模型直接返回 JSON，而是采用：

- 第一次生成自然语言。
- 第二次轻量意图解析。
- 或使用固定按钮触发工具，减少模型自由度。

### 9.4 记忆提炼 Prompt 约束

必须要求模型：

- 只提炼长期稳定信息。
- 不提炼短期情绪为长期事实。
- 不提炼敏感隐私，除非用户明确要求。
- 给出来源。
- 给出置信度。
- 标记是否需要用户确认。

## 10. 隐私、安全与伦理边界

### 10.1 隐私原则

DiaryApp 是日记应用，隐私优先级高于 AI 功能。

必须支持：

- AI 总开关。
- 每类 AI 能力开关。
- 记忆开关。
- 主动留言开关。
- 云端处理说明。
- 清空 AI 生成数据。
- 查看 AI 数据使用记录。

### 10.2 敏感内容处理

敏感内容包括：

- 身份信息。
- 亲密关系。
- 健康与心理状态。
- 财务。
- 精确地点。
- 联系方式。
- 密码、API Key、账号。

处理要求：

- 默认不主动提及。
- 不用于主动留言。
- 不进入未确认长期记忆。
- 不发送到外部渠道。
- 用户必须可删除。

### 10.3 心理健康边界

小墨可以陪伴，但不能诊断。

禁止：

- 给心理疾病诊断。
- 使用“你就是抑郁/焦虑”等判断。
- 制造紧急感。
- 用 AI 替代专业帮助。

允许：

- 温和提醒用户照顾自己。
- 建议休息、记录、联系可信任的人。
- 在极端风险表达出现时，建议寻求现实帮助。

### 10.4 操作安全

必须确认：

- 修改日记。
- 删除数据。
- 创建大量待办。
- 标记待办完成。
- 保存报告。
- 对外发送内容。

必须二次确认：

- 删除日记。
- 批量删除。
- 清空记忆。
- 外部发送私密报告。

## 12. 实施路线图

- 周报生成。

### P4：小墨信箱与主动留言

## 13. 测试与验收策略

### 13.1 单元测试

- 记忆筛选规则。
- 工具权限判断。

### 13.2 集成测试

场景：

- 从对话提炼记忆候选。

### 13.4 安全测试

场景：

- 用户要求删除日记。
- 用户要求发送私密报告。
- 用户表达强烈负面情绪。
- AI 提炼出敏感记忆。
- 旧记忆与新内容冲突。

## 14. 失败模式与风险

### 14.1 人格卡变成死板 prompt

风险：

- 提炼后的小墨变得模板化。
- 每次回复都像在遵守规则。

缓解：

- 人格卡只注入短摘要和示例。
- 不要求固定句式。
- 保留模型自然表达空间。
- 加入“不要机械复述人格设定”约束。

### 14.2 记忆污染

风险：

- 小墨记住错误信息。
- 短期情绪被记成长期事实。

缓解：

- 候选记忆默认待确认。
- 记忆带来源。
- 允许用户修正。
- 降低自动写入范围。

### 14.3 主动留言打扰

风险：

- 用户被 AI 推送烦到。
- 留言像任务压力。

缓解：

- 默认不推系统通知。
- 进入信箱。
- 低频。
- 可关闭。
- 可反馈“不需要这类”。

### 14.4 工具误操作

风险：

- AI 修改或删除用户数据。

缓解：

- 写入必须确认。
- 删除二次确认。
- 操作日志。
- 撤销机制。

### 14.5 成本与性能

风险：

- 长期记忆、摘要、报告导致调用成本上升。
- 移动端后台任务过重。

缓解：

- 本地预聚合。
- 摘要缓存。
- 低频任务。
- 按需检索。
- 用户可限制 AI 使用范围。

## 16. 第一批建议落地任务

如果要从本文进入开发，建议第一批只做这 5 件事：

1. 抽出 `ContextBuilder`，让 AI 请求不再散落拼 prompt。
2. 新增 `PersonaCardEntity`，支持手动创建一张默认人格卡。
3. 新建对话时注入默认人格卡。
4. 增加会话摘要实体，先支持手动“整理当前对话”。
5. 增加“保存这个小墨”的入口，生成可编辑人格卡草案。

这一批完成后，用户最核心的痛点“喜欢的小墨留不住”就能明显改善。

## 17. 当前明确非目标

第一期不做：

- 外部邮件/微信自动发送报告。
- 常驻后台 AI。
- 自动删除或批量修改日记。
- 未确认的长期敏感记忆。
- 医疗/心理诊断。
- 复杂多 Agent 编排。
- 重型动画、WebGL、持续运行视觉效果。
- 直接把全部历史聊天塞进 prompt。

## 18. 开放问题

需要后续确认：

1. 现有 7 个主题的准确名称和色彩 token 是否需要写入 AI UI 规范。
2. 人格卡是否允许多个默认场景，例如“聊天小墨”“写作小墨”“复盘小墨”。
3. 记忆默认是否需要云同步，还是先本地保存。
4. embedding 是否第一期引入，还是先用关键词检索 + 摘要。
5. 周报默认生成时间是周日晚上、周一早上，还是用户自定义。
6. 小墨信箱是否放首页入口、AI 助手入口，还是底部导航。
7. 用户是否希望主动留言有系统通知，还是只在 App 内展示。
8. 桌面版是否与移动端共用同一套小墨记忆。

## 19. 给后续 AI 的阅读提示

如果你是后续接手这个项目的 AI，请先理解以下判断：

- 用户真正重视的是“小墨这个存在是否连续”，不是功能堆叠。
- 不要把人格稳定简单理解为固定 prompt。用户喜欢的是对话中自然形成的语气，需要提炼为结构化人格卡。
- 长期记忆必须可控。任何黑箱记忆都会伤害日记应用的信任感。
- 主动留言要轻，不要做成推送轰炸。
- 工具调用先做读和草稿，再做确认写入。
- 周报、留言、记忆确认都应进入“小墨信箱”这个统一承载面。
- 移动端性能和内存要克制。
- UI 方向是日记、纸张、卡片、柔和色系、轻交互，不是 AI SaaS 控制台。

---

## 20. 总结

小墨升级的核心不是“让 AI 更聪明”，而是让它在 DiaryApp 里拥有连续性。

第一阶段要先保存用户喜欢的那个小墨。  
第二阶段再让小墨拥有可管理的记忆。  
第三阶段让小墨能安全地使用日记 App 的工具。  
第四阶段才让小墨低频主动出现，留下周报、纸条和确认请求。

只要这条顺序不乱，小墨就会从一个 AI 对话框，慢慢变成 DiaryApp 中真正有生命感的长期伙伴。
