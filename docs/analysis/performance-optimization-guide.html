性能优化指南

基于对 DiaryDao、HomeViewModel、TimelineScreen、DiaryDatabase 的深度代码分析，识别出 11 个性能问题并提供具体修复方案。

高优先级 中优先级 低优先级 总结矩阵

高优先级问题

直接影响用户体验的性能瓶颈，建议优先修复。

HIGH 全量加载无分页

getAllPreviews() 将整个 diary_entries 表加载到内存。HomeViewModel、TimelineViewModel、StatsViewModel 各自持有独立副本 = 3 份全量数据。

// DiaryDao.kt:18-19 @Query("SELECT id, title, plainText, ... FROM diary_entries ORDER BY createdAt DESC") fun getAllPreviews(): Flow<List<DiaryPreview>> // 问题: 2000 条日记 = 3 份 x 2000 个对象 // 内存: O(N) x 3 个 ViewModel
// 修复: 引入 Paging3 implementation("androidx.paging:paging-compose:3.2.1") @Query("SELECT ... FROM diary_entries ORDER BY createdAt DESC") fun getAllPreviewsPaged(): PagingSource<Int, DiaryPreview> // ViewModel: val entries = Pager(PagingConfig(pageSize = 20)) { dao.getAllPreviewsPaged() }.flow.cachedIn(viewModelScope)
DiaryDao.kt + build.gradle.kts

内存: O(N) → O(page_size)，初始加载时间大幅缩短

HIGH LIKE 全表扫描搜索

LIKE '%query%' 无法使用 B-tree 索引，每次搜索都是 O(N) 全表扫描。

// DiaryDao.kt:54-58 WHERE plainText LIKE '%' || :query || '%' // 问题: 1000 条日记 = 每次搜索读取 1000 行 // 快速打字时每秒触发多次
// 修复: FTS5 全文搜索 CREATE VIRTUAL TABLE diary_entries_fts USING fts5(title, plainText, content='diary_entries', content_rowid='id') -- 自动同步触发器 CREATE TRIGGER diary_entries_ai AFTER INSERT ON diary_entries BEGIN INSERT INTO diary_entries_fts(rowid, title, plainText) VALUES (new.id, new.title, new.plainText); END -- 查询: O(log N) WHERE id IN (SELECT rowid FROM diary_entries_fts WHERE diary_entries_fts MATCH :query)
DiaryDao.kt + DiaryDatabase.kt

搜索: O(N) 全表扫描 → O(log N) 索引查找

HIGH strftime 阻止索引使用

"历史今天"查询在 WHERE 中对 createdAt 调用 strftime()，导致索引失效，每次全表扫描。

-- DiaryDao.kt:261-303 (4 个查询) WHERE CAST(strftime('%m', createdAt / 1000, 'unixepoch', 'localtime') AS INTEGER) = :month AND CAST(strftime('%d', ...) AS INTEGER) = :day -- 问题: 函数包裹列名，索引无法使用 -- 每次 "历史今天" 都扫描全表
-- 修复: 预计算列 + 索引 ALTER TABLE diary_entries ADD COLUMN createdMonthDay TEXT DEFAULT '' UPDATE diary_entries SET createdMonthDay = printf('%02d-%02d', CAST(strftime('%m', createdAt / 1000, 'unixepoch', 'localtime') AS INTEGER), CAST(strftime('%d', createdAt / 1000, 'unixepoch', 'localtime') AS INTEGER)) CREATE INDEX index_diary_entries_monthDay ON diary_entries (createdMonthDay) -- 查询变为索引查找: WHERE createdMonthDay = printf('%02d-%02d', :month, :day)
DiaryDao.kt + DiaryDatabase.kt

"历史今天": 全表扫描 → 索引精确查找 1-5 条

中优先级问题

影响响应效率和 CPU 占用，但不直接导致卡顿。

MED 搜索无 debounce

每次按键立即触发 combine 管道，对所有条目执行 contains() 过滤。快速打字时每秒 10-15 次 O(N) 过滤。

// HomeViewModel.kt:267-312 // 修复: 添加 debounce _searchQuery .debounce(300L) .distinctUntilChanged() // 效果: 打字期间从 10-15次/秒 // 降至 3-4次/秒
HomeViewModel.kt

MED 4 次独立全列表遍历

dayInfoMap、stats、weeklySummary、selectedEntries 各自独立遍历 allEntries。一次数据变更触发 4 次全量计算。

// 修复: 合并为单次遍历 data class HomeDerivedData( val dayInfoMap: Map<LocalDate, DayInfo>, val stats: HomeStats, val weeklySummary: WeeklySummary, ) // 单次 combine + 单次遍历 val derivedData = combine(allEntries, entryDates) { entries, dates -> ... } .stateIn(...) // CPU 工作量减少 ~75%
HomeViewModel.kt

MED 3 个 ViewModel 重复 tagsMap

HomeViewModel、TimelineViewModel、FavoritesViewModel 各自独立订阅 getAllDiaryTagPairs()，重复构建 Map。

// 修复: 提升到 Repository 层缓存 // 或使用共享 Flow class DiaryRepository(private val dao: DiaryDao) { val tagsMap: Flow<Map<Long, List<TagInfo>>> = dao.getAllDiaryTagPairs() .map { pairs -> ... } .shareIn(scope, SharingStarted.WhileSubscribed(5000)) } // 3 个 ViewModel 共享同一份数据
HomeViewModel.kt + TimelineViewModel.kt + FavoritesViewModel.kt

MED 3 个 DB 查询串行执行

loadReviewEntries() 中 3 个独立查询顺序执行，总耗时 = 三者之和。

// HomeViewModel.kt:128-158 // 修复: async 并发执行 val weekD = async { dao.getByDateRange(w1, w2) } val monthD = async { dao.getByDateRange(m1, m2) } val yearD = async { dao.getByMonthDay(m, d) } // 总耗时 = max(三者) 而非 sum(三者) // 通常提速 2-3x
HomeViewModel.kt

低优先级问题

影响较小或仅在特定场景下触发，可在重构时顺带修复。

LOW getAllTimestamps 全量加载

SELECT createdAt FROM diary_entries 加载所有时间戳到内存，仅用于计算日历圆点。

-- 修复: SQL 层去重 SELECT DISTINCT CAST(strftime('%Y-%m-%d', createdAt / 1000, 'unixepoch', 'localtime') AS TEXT) FROM diary_entries -- 内存: O(N) Longs → O(D) Strings -- D = 唯一日期数，远小于 N
DiaryDao.kt

LOW onOpen 每次删除索引

DiaryDatabase.kt:185-189 的 onOpen 回调每次启动都执行 DROP INDEX，疑似历史遗留。

// DiaryDatabase.kt:185-189 override fun onOpen(db: SupportSQLiteDatabase) { // 每次启动都删除这个索引! db.execSQL("DROP INDEX IF EXISTS index_countdown_items_targetDate") } // 修复: 移除此回调 // 如需删除，在 migration 中一次性完成
DiaryDatabase.kt

LOW 缺少 todo 复合索引

todo_items 的 ORDER BY 模式 (isPinned, isCompleted, priority, sortOrder, createdAt) 无匹配的复合索引。

CREATE INDEX index_todo_items_list_order ON todo_items (parentId, isPinned, isCompleted, priority, sortOrder, createdAt) -- 消除每次查询的临时 B-tree 排序
DiaryDatabase.kt

LOW 批量删除无事务

多选删除 K 条日记执行 3K 次独立数据库调用，无 @Transaction 包装。

// 修复: @Transaction 批量操作 @Transaction suspend fun deleteEntriesBatch( entries: List<DiaryEntry> ) { entries.forEach { entry -> insertTrashEntry(toTrashEntry(entry)) deleteTagsForDiary(entry.id) deleteEntry(entry) } } // N 个事务 → 1 个事务
DiaryDao.kt + HomeViewModel.kt

额外发现：getOnThisDayEntries 使用 SELECT * 包含了完整的 content 字段 (Delta JSON, 通常 100KB+)，但结果仅用于展示摘要。应改用 getOnThisDayPreviews (DiaryDao.kt:271-279)。
