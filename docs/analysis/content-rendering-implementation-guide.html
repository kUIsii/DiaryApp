6 种渲染方案对比

从零迁移到完全保留，逐一分析每种方案的可行性和代价。

check_circle 方案 A: 保留 Delta + 缓存 HTML 推荐

在 Room 中新增 renderedHtml 列，预渲染 HTML 缓存，跳过每次查看时的 Delta 解析。

优势

  • 零数据迁移风险
  • 冷启动从 300ms 降至 ~100ms
  • 保持所有现有格式支持
  • 实现成本最低 (0.5天)

劣势

  • WebView 内存开销不变
  • 仍需维护 deltaToHtml() JS
  • HTML 缓存占用额外存储

text_fields 方案 B: Markdown + Markwon

存储 Markdown，用 Markwon 库原生渲染到 TextView。完全去除 WebView。

优势

  • 原生渲染，无 WebView 开销
  • 内存 ~5MB，冷启动 <50ms
  • 原生文字选择/分享
  • Markdown 通用可移植

劣势

  • Delta→Markdown 有损转换
  • 丢失: 自定义颜色、背景色、对齐、缩进
  • 视频需独立实现 (ExoPlayer)
  • 需要重写编辑器

widgets 方案 C: Compose 原生渲染

解析 Delta JSON 为 Compose 组件树：Text、Image、Video、Divider 等。

优势

  • 完全原生，与 Compose 生命周期集成
  • 原生暗色模式 (MaterialTheme)
  • 原生动画和过渡效果
  • ExoPlayer 直接集成

劣势

  • AnnotatedString 不支持背景色、上标/下标
  • 需手写完整 Delta→Compose 解析器
  • 100+ 块级元素性能不如单 TextView
  • 实现成本极高 (2-3周)

code 方案 D: 混合渲染

Markdown 存储，简单内容用 Compose Text 原生渲染，复杂块（代码高亮、LaTeX）回退 WebView。

优势

  • 90% 内容原生渲染
  • 复杂格式保留完整 CSS/JS 支持
  • 渐进式迁移，可分步实施

劣势

  • 两套渲染路径需维护
  • WebView 高度测量在 Compose 中复杂
  • 原生/WebView 交界处有视觉接缝

html 方案 E: 存储 HTML + WebView

将 deltaToHtml() 输出存入 Room，查看时直接加载 HTML，跳过 Delta 解析。

优势

  • 与方案 A 类似，冷启动提升
  • HTML 可直接用于导出/分享

劣势

  • HTML 体积大于 Delta JSON
  • 编辑时需 HTML→Delta 转换
  • HTML 注入风险需 sanitize
  • WebView 开销不变

android 方案 F: Html.fromHtml() 原生

使用 Android 原生 Html.fromHtml() 渲染到 TextView。

优势

  • 零依赖，Android 原生 API
  • 最轻量

劣势

  • 标签支持极有限（无视频、无代码块）
  • 各 Android 版本渲染不一致
  • 无法处理复杂布局
  • 不推荐用于富文本应用

综合推荐：短期采用方案 A（缓存 HTML），投入产出比最高。中期评估方案 B（Markdown + Markwon）的迁移可行性。长期目标是方案 C（Compose 原生），但需等待 AnnotatedString 能力增强。

推荐迁移路径

分三阶段渐进式迁移，每阶段独立可交付。

1 Phase 1: HTML 缓存 (0.5天)

新增 renderedHtml 列，编辑保存时预渲染 HTML。

// DiaryDatabase Migration: val MIGRATION_13_14 = object : Migration(13, 14) { override fun migrate(db: SupportSQLiteDatabase) { db.execSQL( "ALTER TABLE diary_entries " + "ADD COLUMN renderedHtml TEXT DEFAULT ''" ) } } // EditorScreen.kt - 保存时: val html = webView.evaluateJavascript( "getRenderedHtml()", null ) entry.copy(renderedHtml = html) // DiaryDetailScreen.kt - 查看时: if (entry.renderedHtml.isNotEmpty()) { // 直接加载缓存的 HTML loadDataWithBaseURL( "file:///android_asset/", entry.renderedHtml, ... ) } else { // Fallback: 解析 Delta evaluateJavascript( "setContentFromBase64('$encoded')", null ) }
DiaryDatabase.kt + EditorScreen.kt + DiaryDetailScreen.kt

2 Phase 2: 存量数据迁移 (1天)

后台批量转换已有日记的 HTML 缓存。

// DiaryApplication.kt - 启动时: CoroutineScope(Dispatchers.IO).launch { val entries = diaryDao.getEntriesWithoutHtml() entries.forEach { entry -> val html = convertDeltaToHtml(entry.content) diaryDao.updateRenderedHtml(entry.id, html) } } // DiaryDao.kt 新增: @Query("SELECT * FROM diary_entries " + "WHERE renderedHtml = '' OR renderedHtml IS NULL") suspend fun getEntriesWithoutHtml(): List<DiaryEntry> @Query("UPDATE diary_entries " + "SET renderedHtml = :html WHERE id = :id") suspend fun updateRenderedHtml(id: Long, html: String)
DiaryApplication.kt + DiaryDao.kt

3 Phase 3: 评估 Markdown (中期)

编写 Delta→Markdown 转换器，评估格式丢失程度。

// 需要测试的格式保真度: // [x] 粗体/斜体/删除线 // [x] 标题 (h1-h6) // [x] 有序/无序列表 // [x] 代码块 // [x] 图片/视频引用 // [ ] 自定义文字颜色 --> 丢失 // [ ] 背景色 --> 丢失 // [ ] 文字对齐 --> 丢失 // [ ] 多级缩进 --> 部分丢失 // [ ] 上标/下标 --> 丢失

4 Phase 4: Markwon 集成 (长期)

如果 Phase 3 评估通过，集成 Markwon 实现原生渲染。

扩展能力: 代码高亮与 LaTeX

当前 Delta 支持代码块，但无语法高亮。未来可能需要 LaTeX 支持。

能力 WebView 方案 原生方案 推荐
代码语法高亮 Prism.js (~200KB assets) highlight.js-kotlin 或自定义正则 Prism.js (简单)
LaTeX 数学公式 KaTeX (~300KB assets) JLatexMath (~3MB, 渲染为 Bitmap) KaTeX (WebView)
Mermaid 图表 Mermaid.js (WebView) 无原生方案 仅 WebView

结论：如果 DiaryApp 需要代码高亮和 LaTeX，WebView 仍然是最实用的方案。这些功能在原生端实现成本高且效果有限。建议保持 WebView 作为"高级格式渲染器"，仅对简单内容使用原生渲染。
