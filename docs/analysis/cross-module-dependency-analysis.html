整体架构

DiaryApp 采用 MVVM 架构，Jetpack Compose UI + Room 数据层 + Navigation Compose 路由。所有模块共享同一个 DiaryDao 实例，通过 DiaryApplication.database 访问。

耦合风险点

当前架构中存在的高耦合和潜在问题。

高风险 DiaryDao 单一接口

所有模块共享一个 DiaryDao 接口，包含 80+ 个查询方法。任何新增查询都需要修改此接口，影响所有依赖模块的编译。建议拆分为 DiaryDao、TodoDao、TagDao、TrashDao 等专用 DAO。

高风险 getAllPreviews() 全量加载

HomeScreen、TimelineScreen、StatsScreen 都调用 getAllPreviews() 加载全部条目到内存。当数据量增长到 1000+ 条时，会导致内存压力和 UI 卡顿。需要引入 Paging3 分页加载。

中风险 WebView 生命周期管理

EditorScreen (1639行) 和 DiaryDetailScreen 都使用 WebView，但 WebView 的生命周期管理（stopLoading/destroy 顺序）容易导致内存泄漏。两个屏幕的 WebView 配置代码重复。

中风险 Delta JSON 格式依赖

内容存储使用 Quill.js Delta JSON 格式，解析和渲染都依赖 WebView。如果需要迁移到原生渲染或其他编辑器，需要处理大量已存储的 Delta 数据。建议增加 HTML 缓存字段。

低风险 主题系统硬编码

4种主题模式的硬编码在 Color.kt 中，新增主题需要修改多处代码。GlassCard 等组件通过 when(mode) 分支选择颜色，扩展性有限。

低风险 Navigation 路由参数

EditorScreen 使用 URL 参数 ?diaryId={diaryId}&draftId={draftId}，但参数解析逻辑分散在多个地方。建议使用 Type-safe Navigation (Compose Navigation 2.8+)。

重构建议

按优先级排序的模块化改进方案。

优先级 改动项 影响范围 预计工作量 收益
P0 拆分 DiaryDao
DiaryDao → DiaryDao + TodoDao + TagDao + TrashDao		 全部 ViewModel 2天 编译隔离、职责清晰
P0 引入 Paging3
getAllPreviews() → PagingSource 分页加载		 Home, Timeline, Stats 3天 内存优化、首屏加速
P1 WebView 工具类抽取
Editor 和 Detail 共享 WebView 配置和 JS Bridge		 Editor, Detail 1天 代码复用、统一维护
P1 HTML 缓存字段
DiaryEntry 新增 cachedHtml 字段，避免每次 Delta→HTML 转换		 Detail, Export 1天 详情页加载速度提升
P2 Type-safe Navigation
URL 参数 → Kotlin Serialization 路由		 NavHost, Editor 1天 类型安全、可维护性
P2 主题系统重构
硬编码 → ThemeSpec 接口 + 动态注册		 Theme, Components 2天 可扩展性、自定义主题

注意：DAO 拆分和 Paging3 引入是最高优先级的改动，它们直接影响应用的性能和可维护性。建议在进行其他功能开发之前先完成这两项基础重构。
